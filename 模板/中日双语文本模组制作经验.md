# 中日双语文本模组制作经验(通用方法论)

> 源自 2026-09《FINAL FANTASY RESONANCE DEMO》(UE5)实战提炼,并整合《空之轨迹1st》社区 mod 调研(见 §8)。项目级细节与证据路径见 FFRS 项目目录的《进度记录.md》《CHECKPOINT.md》与 UE 专用完整版《双语文本Mod制作经验(UE通用).md》。
> **系列定位**:日文原文 + 简体中文对照的**中日双语** mod;下文「日文/中文」即双语两侧。
> **结构说明**:§1–§6 为引擎无关主干;§7 富文本、§8 振假名为两个**专项**(方法引擎无关,案例覆盖 UE 与 FALCOM);§9 虚幻引擎专用;§10 其他引擎速查;§11 移植检查清单。非 UE 项目跳过 §9。

## 1. 总体思路:取材与显示分离,零代码注入

游戏既然自带中日两种语言,就不需要任何翻译工作——把「日文 + 中文」**拼成单个字符串**写进中文文本数据:

- 游戏内选「中文」= 显示双语,选「日文」= 纯日文,**语言开关天然就是 mod 开关**
- 优点:不碰代码、无性能损耗、游戏更新后重跑管线即可
- 边界:双语两段只能同样式(块内分别指定字体/颜色/字号需运行时注入,默认排除,详见 §7);纯贴图文本(logo、部分标题元素)不在此路线内

## 2. 双语版式(核心经验)

**两种基础版式(项目术语,后续项目沿用)**:

- **标题式**:`日文 中文` **同行**、中间两空格(或全角空格;单半角空格太窄)——适合**单行**短文本(按钮、词条名、菜单项、状态词)。
- **段落式**:`日文`块 + 边界 + `中文`块——适合对话/长文本。**边界自适应原文段落结构**:日/中块内**只有换行没有空行**时,边界只用**换行**;块内**含空行**(多段)时,边界**额外加一个空行**。

★**版式判定规则(FFRS 两轮实战教训,通用)**:

1. **任一侧(日文或中文)自身含换行(多行/多段)时,必须用段落式,禁止把中文以标题式拼在多行日文的末行后**——「JA1\nJA2  ZH1\nZH2」里中文像日文的续行,极难阅读(FFRS 案例:着色器编译界面)。
2. **段落式的边界行数必须跟随原文结构,不要一律加空行**——固定高度文本框里多一行就溢出(FFRS 案例:难度选择说明为固定 4 行框,空行边界渲染 5 行即溢出,换行边界恰好 4 行)。
3. 单行短文本才用标题式(段落式会让按钮/菜单多占行)。

**实现建议**:合并脚本做 **auto 三段判定**(日中两侧均单行→标题式;任一侧含换行无空行→段落式·换行边界;任一侧含空行→段落式·空行边界)。判定须**同时读两侧原文**,且键映射**大小写敏感**(键常有 `OFF`/`Off` 这类双变体)。auto 按分组/命名空间粒度启用、**试玩反馈驱动推广,勿预先全局套用**(FFRS 先例:教程、标题菜单两个分组先后启用)。回滚某分组 = 把该组改回固定模式重跑。

★**版式模式总表(统一口径;组→模式映射与渲染实现集中在合并脚本,DQ7R 参考实现 `workspace/merge_resident.ps1` 的 `$wl` + `Get-LayoutMode`/`Merge-Text`/`Merge-CsFlex`/`Merge-DlgPages`)**:

| 模式(脚本名) | 定义 | 适用 |
|---|---|---|
| 标题式 `title` | `日文␣␣中文` 同行、两空格 | 单行短文本(按钮/词条名/菜单项) |
| 段落式·无空行 `para_nl` | 日文块+**换行**边界(强制,不随原文自适应) | 容量紧张的段落文本(用户逐组指定) |
| 段落式·带空行 `para_blank` | 日文块+**空行**边界(强制) | 容量充裕的段落文本(如章节梗概) |
| 段落式·auto `auto` | 边界自适应原文:两侧均单行→标题式;任一侧含换行无空行→换行边界;含空行→空行边界 | 混合组(教程/物品说明等) |
| 行交错 `cs_flex` | 逐行"日文行+中文行"交错;行数不等时贪心配对+余行追加;日文行数超容器上限的键跳过合并 | 无框过场字幕(硬行数上限、无翻页) |
| 分页对白 `dlg_pages` | 行级单元+链式配对成顺序句对流:日句保留原文换行;中文仅当拍平能使句对单页化时拍平;句对结束页补空行独占,下对起新页;配对失败回退块式(日文段前+中文段后) | 名牌对白框/多行确认框等可翻页容器 |

注:`para_nl`/`para_blank` 是**用户逐组指定**的强制边界;`auto` 是按原文结构的自适应判定。三者的取舍见上方版式判定规则 2。

★**固定高度+自动分页的对白框(DQ7R 实战,通用)**:

游戏常见两种对白容器:**无框过场字幕**(固定 N 行、无分页、超行截断)与**名牌对白框**(固定 N 行+▼自动翻页,空行占一行计数)。处理经验:

1. **键前缀↔UI 类型不可靠**:同前缀混含多种容器、同块号跨场景对应不同 UI。须用游戏内截图文本反查样例键建立映射,小批试探验证后再铺全量。
2. **无框字幕**:合并文本受硬行数上限约束,超出即丢字。对策=条件式行交错(逐行"日文行+中文行";两侧行数不等时贪心配对+余行追加),原文自身超限的键跳过合并保持原版。
3. **分页对白框·核心原则:句对邻接**。句对=日文单元(**原文换行永远保留**)+对应中文;句对按序排列、**可跨页**;句对结束页补空行独占,保证下一句对从新页开始;页与句对非一一对应。三个反例教训:①"拍平日文"(删句内换行强求一句一行)破坏原文排版——日文作者常在句中换行;②"一页一句对"硬约束(句对超页即回退块式)违背邻接原则;③中文拍平须**仅当能使句对单页化时才做**(超页句对拍平无收益且毁中文排版),中文拍平不加空格(中文无句内空格习惯)。
4. **切句与配对(DQ7R 最终形态:行级单元+链式)**:单元=连续行直到以强终止符(。!?)结尾的行——**同行短句自动合并**(如"そら!　そら!"两感叹同行,按终止符硬切会各自独占一页);省略号常是拖音不算结句;富文本收尾标签(如 `</color>`)会被切成独立"句子",必须黏回前句,否则配成**纯标签空白页**。链式配对:行级单元 1:1 且每对终止符数相等(=中文镜像同行结构)→ 日文单单元时中文全部归并 → 句级 1:1 → 中文行数==日文句数且行尾强终止符的粗略逐位 → 块式。官方中文常**并译**(两句并一句)、**拆译**(一句拆两句)或**镜像日文换行**,链式各接一类;行尾逗号/顿号是并译特征,粗配对须防错位。
4b. **守卫陷阱**:去占位符后剩余≤N 字的"模板键"守卫会误杀真实短句(如"{HERO}收下了{I_NAME}!"剩余"收下了"3 字被跳过,整句失去双语)——模板判定应要求剩余部分**无 CJK**;物品名/人名等占位符双语替换是数据层无奈之举(同名键兼作独立显示与运行时替换源)。
5. **流程纪律**:先小批试探键标定(容器行数上限、折行宽度、空行是否翻页),再铺全量;凡改变用户可见输出的实现取舍,动手前与用户确认。

**★对话/聊天类表格禁用标题式、统一整块段落式(空轨1st 实机)**:短句对话走通用"≤50 字符=标题式"规则会出现「日文　中文」同行,与交互对白的日/中两行观感割裂——按表名单强制段落式(`PARA_TABLES`)。行级交错(日中逐行交替,行数相等才启用)观感不一,玩家实测后**决策弃用统一整块式**(实现注释保留备查);DQ7R 的行交错经验(`cs_flex`,模板 §2 版式模式总表)适用于**固定行数/无翻页容器**,本作对白框非固定行数,整块式反而利于下条规则。

**★溢出缓解·中文末两行拍平(空轨1st,玩家规则)**:整块段落式合并后**超过 5 行**且中文占多行时,把**中文侧最后两行拍平**(换行直接移除)——引擎按框宽重新折行,显示行数**单调不增**,常省出 1 行,避免对白框/弹窗末行被截。只动中文块、不动日文块;对手工换行的书籍/攻略页同样适用。注意:跨**多个调用**拼屏的溢出(一次显示连续多个对白调用)数据层不可见,此规则管不到,属引擎分页行为(文本不丢,翻页显示)。

## 3. 适用性判定(动手前)

1. **引擎判定**(看安装目录特征):`*.utoc/*.ucas` → UE5 IoStore(转 §9);`*_Data/` → Unity;`www/js` → RPG Maker;FALCOM 系见 §10;其他 → 查社区资料确定引擎与文本格式。
2. **文本数据形式**:能否找到标准本地化数据(UE = `.locres`;其他引擎各有文本表/脚本格式)。搜不到 → 文本可能在自定义表、硬编码或贴图里 → 换路线(数据表编辑或运行时注入),工作量上一个档次。
3. **资源包是否加密**:解包时即知(加密需密钥,社区常能找到)。
4. **目标语言标识/目录名**以包内实际数据为准,不要凭猜。
5. **★空壳存根陷阱(「声东击西」,DQ7R 实战)**:标准本地化文件**存在**但全是几十字节空壳(locres 仅 37 字节、导出 0 条)——文本真身在别处(该例为 IoStore 容器内自定义 DataAsset `DA_ResidentTextData_*`,语言目录用 `JP/CNS/CNT` 别名而非 `ja/zh-Hans`)。判定:解出后先看文件大小与条目数,异常小即存根;再全量列容器路径检索真载体(**`retoc list` 必须带 `--path`,否则只有十六进制包 ID,字符串检索必失效**)。引擎版本 exe 里可能搜不到,可用 modding 社区页面(如 RenoDX)佐证。

## 4. 文本处理规则(key 层面)

- **★格式/模板键陷阱(高频坑,务必设防)**:文本数据中有一类键的值**本身是格式模板**(如 `第{Chapter}章 {Name}`、`{Num}个`),由游戏填充实参后显示。这类键**绝不可双语拼接**——拼成「日文模板 + 中文模板」后,游戏会对同一实参**各应用一次模板,同一内容显示两遍**(FFRS 曾因此导致存档行章节名双显,症状酷似"存档烘焙文本""双字段渲染",排查数轮)。**判定**:把值中的占位符全部去掉,剩余文本极短(经验阈值 ≤4 字符)即为纯模板;**处理**:跳过拼接、保持原版(合并脚本设自动守卫 + 输出异常报告);若模板本身有官方瑕疵(如某语言版缺空格),可写入修正后的**单语**模板。
- **★printf 格式化占位符禁双语(崩溃级,Trails1st 实机确认)**:与 `{}` 模板键不同,还有一类值是 **printf 风格格式化串**(含 `%s`/`%d`/`%f` 等,典型=系统通知/确认弹窗:「%sのＳＴＲが%d上がった！」)。双语拼接会**两侧的占位符一并保留**,合并串占位符数量翻倍;若引擎用该串做 sprintf 类格式化,**多出的占位符消费栈上垃圾实参 → 访问违例闪退**(Trails1st t_text 38 条,出场 transition 必崩、读档后可玩一阵,症状极易误判为"内存泄漏/偶发崩溃",二分 8 轮才定位)。**判定**:合并前后 `%[-0-9.]*[a-zA-Z%]` 计数不相等即禁拼;**处理**:该键保持日文单语(回滚名单),崩溃风险不值得冒;系统通知类维持单语属可接受代价(高频但短语,双语价值低)。**守卫盲区教训**:逐侧校验"占位符集合一致"拦不住它——两侧各自自洽、合并后才翻倍;守卫必须校验**合并结果与原文的占位符数量一致**。
- **探针法(定位神器)**:给嫌疑键写「测试甲/测试乙」等标记值部署后观察 UI 各段文字,一轮即可确定"哪段文字来自哪个键/哪个字段"——定位模板键、双字段渲染、漏覆盖都靠它;也是 §7/§8 判死检查的实测手段。
- **键分组即语义分类**:键的命名空间/表名/ID 前缀通常就是语义分类(界面、弹窗、章节剧情、词条名/描述、地名……),按组整批纳入最划算,不要逐条审。
- **开场文本定位**:让玩家提供最先看到的几句原文,反查 key,再取同组整批。
- **「假双语」排除**:某些键的日文版本就是英文样式(状态词、SYSTEM 菜单等),拼接后出现 "Continue Continue" 这类重复。**推广规则(推荐写成脚本自动判定)**:两侧文本**都不含 CJK 字符**时跳过拼接、保留原文本。正则:`[\u3040-\u30FF\u3400-\u9FFF\uF900-\uFAFF\uFF66-\uFF9F]`(假名+汉字区块)分别检测两侧,均未命中才跳过。边界:仅一侧是英文样式(另一侧有正式译文)时仍应合并。
- **占位符值重复**:「将以{difficulty}开始游戏」里占位符的值若本身是被拼接的词条(如 Normal→"Normal 普通"),会在两个句子里各出现一次。值类词条可考虑保持单语,或接受。
- **「完全相同串」**:日中共享同一汉字词(如「学生」)拼接后是「学生 学生」——接受重复显示(有差异的串本就正常合并,不受影响);日后嫌碍眼再加"完全相同即跳过"开关。
- **识别无效条目**:数据里可能混有 ROM 标注、调试文本,合并前按内容抽查剔除。
- **结构一致性守卫**:拼接前校验两侧 `{占位符}` 集合与 `<标记>` 结构一致,不一致跳过并写异常报告(防合并破坏游戏解析)。

## 5. 合并管线与工程纪律

**标准管线(抽象六步)**:解包资源 → 导出日/中两语言文本 → 按 key 合并(按 §2 版式)→ 写回中文侧 → 重打包/部署 → 试玩验证。

- **文本内容永不进入对话上下文/日志**:脚本在文件层面处理,只输出统计(总条数/合并数/跳过数);命令输出先 `grep/head`;异常清单写本地报告文件。
- **Windows 控制台编码坑**:Git Bash 控制台多为 GBK,直接查看 UTF-8 的 CSV/文本会「乱码」——文件没坏,是显示问题;需人工看内容时用 PowerShell 并先设 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`。
- **key 清单就是断点**:每轮追加的分组标注版式模式,清单即生效范围即回滚单元;脚本与规则表入库,重跑一轮控制在分钟级。
- **二进制结构手术前两条铁律**(空之轨迹1st 字体三轮实机试错的教训):①**先查同游戏"第三语言 mod"的字体/文本工具链**——做全文本本地化的 mod 必然解决过字形问题,其格式文档一步顶数轮逆向(Arabic mod 的 FONT_SPEC.md + 俄语包的 loose DDS 若在第一轮字体实验前先读,可省三轮试错);②**验证结构不变量**(排序/索引/链式引用)——追加式改写只适用于"引用重定向"类结构(脚本字符串池、归档条目),**有序查找表必须整体重排**;看似"压缩数据"的未知字段要先对照规范解义,往往是坐标/索引/通道而非数据本身。
- **PowerShell 陷阱清单(DQ7R 实战,逐条踩过,症状都极隐蔽)**:①PS 5.1 把无 BOM 的 UTF-8 脚本当 ANSI 读,中文注释/路径会破坏语法或查错路径——脚本全 ASCII 或存带 BOM UTF-8;②十六进制字面量 ≥0x80000000 按 int32 回绕成负数,与 `[BitConverter]::ToUInt32` 比较恒假——改用十进制或 `[uint32]` 收窄;③**`BinaryWriter.Write($byteArray)` 会把 byte[] 转成 bool 只写 1 字节(0x01)**——数组写入必须用 3 参数重载 `Write($b,0,$len)`(症状:文件悄悄变短、刚写的内容"消失");④`foreach` 遍历泛型 Dictionary 直接产出 Key 而非 KeyValuePair,`$kv.Key` 恒为 null——用 `$dict.Keys` + 索引器;⑤函数返回数组防展开用 `,$arr`;⑥函数内 @() 里的复合表达式有类型推断怪癖,拆步赋值更稳;⑦**Git Bash 的 grep 对含 NUL 的二进制文件完全失效**(连确定存在的 ASCII 子串都报 0 命中,`-a` 也不可靠)——二进制字节搜索一律用 PowerShell 逐字节循环或 .NET `SearchValue`,grep 的"0 命中"对二进制不可作证据;⑧**PS 函数返回值会把单元素数组展开成裸字符串**——调用处 `$s[$i]` 随之变成按**字符**索引(症状:配对输出只剩两边首字符、类似"父  你"),调用处必须 `$x = @(Fn ...)` 强制数组化。
- **版式方案迭代纪律(DQ7R 实战)**:对白/字幕类双语版式不能只看合并数据是否正确——必须实机走完**翻页/滚动/截断**全路径再评价;句子级交错(逐句同行配对)虽能保证"翻页不拆散正在读的句对",但会割裂原文的行节奏(拟声词重复句"そら そら"、多行句对强行内联溢出),已实测回退;每次版式改动只动一个变量,用户反馈定位才能落到具体规则上。
- **自定义二进制格式逆向的验证纪律(DQ7R 实战)**:结构假设必须"全文件解析到 EOF 才算成立",手算对齐极易一叶障目——先写探针脚本程序化验证,失败时打印失败点±32 字节十六进制上下文;解析器带逐字节 resync,未解码区域写回时**原样拷贝**,只动已解析记录;每次改写后做**零改动往返自检**(空改动重建必须与原文件逐字节一致)+ **重导出比对**(改写键=新文本、未触碰键=原文、结构统计一致)。FString 长度语义按 UE 标准假设(UTF-16 len=码元数+1);首条特殊记录当不透明头原样拷贝即可推进,勿在其语义上空转。管线中消费精确字节中间态的步骤**不跨代理/会话边界靠自然语言交接**——续跑一律重跑脚本(状态在文件里,不在对话里)。
- **首轮分组顺序:菜单/设置/存档等界面文本优先于剧情对白**(FFRS 先例,《空之轨迹1st》复验):界面文本玩家进游戏立刻看到、验证成本最低,最能直观证明"双语奏效";剧情对白量大且渲染未知项(换行、溢出、字形)多,放后续轮次。数据侧通常对应:界面文本在数据表(键名 + 定长行 + 文件内偏移指针),对白在脚本字节码;表合并用**跨语言同表行 diff** 定位译文字段(两侧都合法解码且文本不同、至少一侧含 CJK 才算译文对;键名/文件名/路径类自动被"双无 CJK"守卫排除),行对齐优先按唯一键列,行数不齐(版本差异)只合并键匹配行并记录,守卫复用 §4。
- **迭代循环**:玩家报告问题原文 → 反查 key → 改规则/清单 → 重跑管线 → 部署,**每轮几分钟**;溢出/漏项由试玩反馈驱动,不预先做全量分析。

## 6. 部署与分发

- **实验阶梯(先便宜后贵)**:①官方支持的补丁机制(额外文件/挂载/覆盖目录)→ ②重建主资源一锤定音(确认"能否生效"后即为最终方案)→ ③运行时注入(**默认排除**:分发、封号、版本维护成本全最高)。
- **区分「验证实验」与「分发形态」,两者可以不同**:阶梯排序解决的是"先验证哪条路"——最严格路径先测,通过即管线输出端到端得证;最终分发形态按体积/共存/抗更新/第三方信任单独权衡(对应 AGENTS.md 分发排序:sidecar → loader → 安装器)。**loose file loader(代理 DLL 重定向文件读取)不等于 ③ 的"运行时注入"**:不碰内存、不挂钩渲染逻辑,只是文件系统层的覆盖通道;引擎若无官方补丁机制,社区成熟的 loose loader 即 sidecar 等价物,验证通过后可作首选分发载体(《空之轨迹1st》实例:整包替换分发 24.4 MB,loose 仅 8.3 MB)。采用前仍须确认:loader 对该游戏版本的实测有效性、维护活跃度、许可证;游戏大更新后需复验 hook。
- **★官方原版必须先备份**(最好放游戏目录外);用**哈希基线**识别官方版本与已装版本;安装脚本要有:拒装保护(版本不符拒绝)、安装自检、幂等重装、`-Uninstall` 还原。
- **失效场景**:平台"验证文件完整性"和游戏更新都会还原官方文件 → mod 消失,重跑管线即可(管线脚本化后为分钟级);游戏更新后**必须**核对官方哈希重建基线,不得用旧解包数据覆盖新版本。
- **小体积分发**:优先只携带改动数据 + 安装脚本(FFRS 分发包 ≈17MB:安装脚本 + 解包工具 + 改动文件),由脚本在用户机上基于官方原版重建;若平台不支持则退回全量重建分发。
- **mod 文件命名 = 加载序 + 语义可辨识,两者都要**:UE `_P` 后缀=补丁容器优先;`z` 起头保证按字母序挂载在官方 `pakchunk*`/`global` 之后(最后挂载者覆盖同名包)。但纯排序前缀(`zzz_`)可辨识度差、易被当成恶意软件(杀软误报、玩家不敢装)——DQ7R 项目改用 **`zhsjp_`**(zh-Hans+JP 双语含义)起头,语义与排序兼顾;命名经验写入本项目 AGENTS.md 项目档案。
- **sidecar 覆盖实测(DQ7R/UE4.27 IoStore)**:`Content/Paks/` **根目录**放 `_P` zen 三件套(.pak+.utoc+.ucas,可只含改动包,包 ID 与官方一致)即可覆盖官方同名包,后挂载者胜;`~mods` 子目录**不一定**被扫描——exe 里 grep 不到 `~mods` 字符串基本可断定无效,直接放根目录。
- **★判死一个机制前,先验证测试样本本身(DQ7R 实教训)**:部署补丁后"画面没变化"有两种原因——机制失效 **或 测试的键根本不出现在被观察画面**(键名语义有欺骗性:DQ7R 的 `UI_Mainmenu_*` 实为游戏内道具/咒文消息,标题菜单另有键族)。判死流程:①用屏幕可见字符串**反查键**确认"改的键=看到的键";②给 1–2 个键写入探针标记值部署观察;两者通过仍无效才判机制死。DQ7R 曾因跳过此步把 sidecar 误判判死,绕道重建主容器一轮后才翻案。

## 7. 富文本专项(块内字体/颜色/字号/标记样式)

**目标**:双语块内给日文/中文分别指定字体、颜色、字号。**默认结论:数据层做不到就放弃——注入是唯一出路且默认排除**。动手前做三步判死检查(约 1 小时):

1. **文本层标记扫描**:全量扫两语言文本值里的 `<...>` 标记形态——游戏自己在文本里用什么标记,数据层才可能控制什么;若只有输入图标类标记(UE 常见 `<IA tag="X"/>`),则无样式语法可用。
2. **样式/渲染层配置检查**:转出富文本装饰器/样式定义检查其序列化数据——若样式定义不含字体/颜色/字号成员(即样式硬编码在引擎原生代码),数据层无入口;自定义渲染控件可先查脚本成员有无 Color/Opacity/FontSize(UE 手段见 §9.5)。
3. **探针实测(§4)**:给 1–2 个常显键写候选标记(带已知可解析标记作阳性对照),部署观察——FFRS 实测:对话/字幕控件族对一切候选文本标记**原样文字渲染**。

**FFRS(UE5)判死案例**:①文本层唯一标记=输入图标 `<IA/>`;②样式资产序列化为空(仅标签名,字体/颜色/字号全在原生代码)→ 资产层无入口;③探针全标记原样渲染。**结论:仅靠数据层无法对中日分别指定样式,双语块两段只能同样式**(§1 边界依据)。字体"跨界面不一致"现象的机制解释见 §9.5(UE 复合字体文化分组),同样文本层不可控。

**残余选项**:游戏文本若真有样式标记语法则按其语法使用;否则只剩运行时注入(默认排除)。

**DQ7R 色名实测(DQ7R 实战,五轮探针)**:游戏文本自带 `<color=Yellow>...</color>`(开闭配对)时样式语法可用,但引擎**只认极少数色名白名单**——实测仅 `Yellow`/`Blue`/`Red` 生效;hex 值(`#RRGGBB`)与其余全部常见色名(Aqua/Cyan/LightBlue/Gray/Green/DarkGray/Silver/White/Black/Orange/Lime/Olive)一律不渲染(不显色、无标签残片=标记被剥离)。**控件族差异**:分页对白框/弹窗类解析颜色;无框过场字幕控件对一切标记"剥离但不应用"(颜色判死,与 FFRS 字幕判死一致)。色名白名单在引擎内走 FName 比较,exe 字符串层挖不到表,只能逐轮部署探针枚举(候选集中到进游戏立即可见的少数键上,一轮多键各测一色)。

## 8. 振假名(ruby)专项

**目标**:①汉字上方标注假名读音(真 ruby,日语学习向);②借 ruby 通道在正文上方显示第二语言对照(《空之轨迹1st》字之理的中/英对照即此思路)。**可行性与引擎/厂商强相关,与 UE 本身无关**:FALCOM 引擎脚本格式**原生支持振假名标注**(引擎直接绘制 ruby);UE/Unity 等通用引擎默认无 ruby 能力,除非游戏自研。

**判死检查三步法(动手前,约 1 小时)**:

1. **渲染能力关键词扫描**:对游戏数据全量二进制 grep `Furigana`/`Ruby`/`ルビ`/`PHONETIC`(注意内容词误命中,如 FFRS 英文文本的 "Ruby Cave" 是地名)。
2. **文本层标记扫描**:游戏文本数据是否自带 ruby 标记语法(FALCOM 脚本自带;UE 游戏通常只有输入图标类标记)。
3. **参照同引擎/同类游戏社区实现**:确认"别人怎么做到的"——已知实现全部依赖引擎原生 ruby 渲染层。

**《空之轨迹1st》(FALCOM,原生支持振假名)两个社区 mod 实例**:

- **Kana Assist(Nexus #64「Dual Subtitles JP-EN Text with Kana Assist」)**:xinput1_4.dll 代理 DLL + loose file loader(Sora1),替换脚本文本数据(script/table),借**引擎原生 ruby 标注**显示假名注音,并与官方英文对照双显。数据路线,无内存补丁。
- **字之理(trails_in_the_sky_text_tool)**:外部内存补丁式辅助程序(C#:OpenProcess 读写 + NtSuspendProcess 挂起 → sora_1st.exe 的 SHA-256 与补丁点指令签名校验 → 固定偏移写跳转壳代码 → 恢复运行,退出可还原;不注入 DLL、不改游戏文件、强版本锁定)。壳代码以前导空格为标记把注解字符串路由进引擎**已有的 ruby 绘制函数**(源码注释 "Source-game ruby is preserved",原生 ruby 保留),配合字形缓存重置刷新;磁盘侧另配 SCP 脚本标注补丁与可选字体安装器。**创新在投递通道(内存补丁 vs 脚本替换),渲染层仍 100% 依赖引擎原生 ruby**。

**通用结论(FFRS + 空轨两 mod 交叉验证)**:所有已知振假名实现都依赖引擎**原生 ruby 渲染层**;数据层补丁只能"喂内容",造不出渲染器。**可行性判定**:①引擎原生支持(如 FALCOM)→ 数据补丁即可实现,优先数据路线;②引擎无原生能力(如 UE;FFRS 全 pak 关键词零命中)→ **判死**,唯一出路是注入级自建渲染器(开放式逆向,默认排除)。判死后残余:行内括号注音(「漢字(かんじ)」式,非真 ruby,破坏排版,默认不做)。

## 9. 虚幻引擎专用(UE4.26+ / UE5,含 IoStore)

### 9.1 文本数据

- 本地化在 `Content/Localization/<模块>/<语言>/xxx.locres`(`repak list 游戏.pak | grep -i localization` 确认);`.locmeta` 列语言清单。
- **UnrealLocres**(v1.1.0 实测)做 locres↔CSV:`export -o` **务必指定输出路径**(默认写当前目录同名覆盖);`import <locres> <csv> -o <新locres>`;**先确认列语义**(表头 `key,source,target`,哪列装真实文本)再写回,写回后**重新导出复核一次**最保险。新引擎版本格式不兼容时试 LocResUtility 或 pip 的 unreal-locres。

### 9.2 工具链(全免费、绿色单文件)

[repak](https://github.com/trumank/repak)(pak 解包/打包,`pack --version V11 --compression Oodle`,挂载点默认 `../../../` 通常正确)、[UnrealLocres](https://github.com/akintos/UnrealLocres)、[retoc](https://github.com/trumank/retoc)(IoStore utoc/ucas 解包/转换,含 to-legacy/to-zen)、UAssetGUI(UAssetAPI,experimental)。注意 repak 旁必须放 oo2core DLL,否则会尝试联网下载而超时。

### 9.3 部署路径(实测结论)

1. **先试 `_P` 补丁 pak**(`Content/Paks/任意名_P.pak` 或 `~mods/`),多数 UE4/5 游戏直接生效。
2. **不生效 → 对照实验(一锤定音)**:备份官方原版 pak → 完整解包 → 覆盖双语 locres → 相同参数重打包 → 原文件名顶替。能启动+双语 = 重建法即最终方案(该游戏白名单式挂载,sidecar 判死——可用文件锁探针证实:游戏运行中是否打开过补丁文件);能启动+无双语 = 文本在 IoStore 侧,转注入;不能启动 = 立即还原(有自定义种子/校验)。
3. **自动化**:把重建法写成 install.ps1(官方哈希基线/自动备份/拒装保护/自检/幂等/卸载),即分发形态。
4. 挂载失败也无需逆向挂载规则——重建主 pak 的代价只是体积与"校验/更新后需重装",脚本化后可接受。

### 9.4 key 与 CSV 细节

- `Namespace/KeyName` 的 Namespace 即语义分组(`ST_UI_*`、`ST_C01_001_xx` 章节剧情等),整组纳入。
- **键大小写冲突真实存在**(如 `RadioButton_OFF` vs `RadioButton_Off`):合并与映射一律用大小写敏感字典,冒烟测试含重复检测。
- CSV 字段含逗号/换行,解析必须 CSV 感知(PowerShell 用 `Import-Csv`;手写解析会把多行值截断)。

### 9.5 字体资产观察法(为 §7 富文本调查提供 UE 手段)

- **复合字体按文化分组**(UFont/CompositeFont.SubTypefaces:默认组(常为日文)+ `zh-Hans`/`zh-Hant`/`ko`/拉丁 各绑独立 FontFace):游戏以何种文化运行,双语块就以该文化的子字体为基准渲染;缺字形逐字形 fallback 到其他组或引擎 `DroidSansFallback`。**机制推论**:「不同界面字体不同」= 不同 UI 域引用不同复合字体;「块内日/中自动异字体」部分天然存在(日文专有字形落到别的组),但分布由字库覆盖决定,**文本层不可控**(判死结论见 §7)。
- **观察方法**:`retoc to-legacy <整个Paks目录> <输出> --filter Font --no-shaders --no-script-objects`(**输入必须是目录**,单 utoc 会因跨容器导入解析而全部失败)→ legacy .uasset 用 `grep -aoE '[ -~]{3,}'` 可读出 FontFace 引用与文化分组字符串;face 语言归属按命名(SCGb4/GB30=简中、B5HK/TC=繁中、Pr6N=日文)交叉判断。编辑用 UAssetGUI → `retoc to-zen` 回包——experimental,改前先出报告评估。样式/装饰器资产的序列化检查同样走这条链(§7 判死检查第 2 步的 UE 实现)。

## 10. 其他引擎速查

- **RPG Maker(MV/MZ)**:`www/js/` 特征;文本在数据表/事件/插件体系,找数据文件后按 §1–§6 管线走。
- **Unity**:`*_Data/` 特征;文本可能在 I2 Localization / Unity Localization 等方案的资产或表里,先定位文本载体。
- **FALCOM(轨迹系列等)**:FPAC/SCP 归档与脚本格式;**脚本格式原生支持振假名标注**(振假名可行性的前提,社区两 mod 先例见 §8);文本数据定位后接标准管线。社区两类先例**性质不同,勿混为"注入"**:loose file loader(xinput1_4.dll 代理,重定向文件读取,数据层覆盖通道,分发排序中的 loader 层)与内存补丁辅助程序(CE 式读写进程内存,属 §6 ③运行时注入,默认排除)。
- **FDK 字体系统(空之轨迹1st 重制版实测,第四轮验证通过)**:字形位图**不在字体 pac 里**,而在图集贴图 `asset/dx11/image/font_0.dds`(4096²,BC7_UNORM,**双通道复用**:R/G 各存一半字形,表项 flag 选墨水通道;数字另有 1024² number_fonts.dds);字体 pac 里的 font_0.fnt(FCV/FLTI)只是**索引表**:24B 表项 = code u32 + int0 u32 + 8×u16(图集坐标 GNF_X/Y、宽高、flag、度量 half 系),表须**严格按码点升序**(引擎按序查找)。**跨语言字形路线**:字形编码与图集布局绑定,跨版本字节级并包/顶替必败(实测乱码);正确做法 = **图集矩形移植**——扫描本语言图集空闲带,把所需字形矩形从他语言图集原样拷入(保留通道/内边距/度量),.fnt 加坐标重指记录,整体重排后 texconv 重编码 BC7;DDS 在 image 包内,可就地追加补丁(截断可还原)或按俄语包先例 loose 分发。**权威规范**:Arabic mod 仓库 `FONT_SPEC.md`(含 ui_bold 描边着色器对 cell 边缘的要求:字形墨水不得贴边,需 ≥6px 内边距,vanilla 字形自带)+ `build_arabic_atlas.py` 配方。
- **★非对白显示串也可数据层合并(空轨1st 实机)**:#scp 里除对白调用(kind==3, arg0=0x40000005)外还有大量**非对白显示串**——过场地名横幅、NPC 名牌、动作/交互标签、路标里程、教程标题——同为调用字符串参数,可**按调用结构(函数/调用序/参数位)跨语言配对**合并,守卫沿用对白管线(禁 ruby)。要点:配对签名须把**引用型参数值(0xC0<<30|off)掩码**后再比对(引用跨版本必然不同,语义常量须相同);两版调用顺序差异会造成个别条目交叉配对(路标里程串到另一条,量小可接受,记已知瑕疵);opcode 内联串(op0/34/35,数量大)含开发注释,未甄别前不可盲并。
- **★图集"空闲带"不真空闲——保留区陷阱(空轨1st 实机定案,伪影级)**:扫描判定"全空"的图集尾部区域可能被引擎**按固定坐标保留使用**(注音/小字形/运行时缓存路径按写死坐标取样,不走 fnt 索引)。往里拷字形 → 引擎那条路径把新字形像素当自己的数据画出来(症状:注音位出现"条形码"状色块伪影,且只在该语言字形在场时出现)。**判别法(零构建二分)**:①"合并索引表+原版图集"→ 伪影消失且新语言字形空白 = 索引表无辜;②"原版索引表+合并图集"→ 伪影仍在 = 图集单独致病;本例①②均阴性 → 触发条件=索引表+像素同时在场,伪影位置=新字形的注音位 → 第三轮"**同管线重定位字形带到另一空带**"验证:伪影消失+字形正常 = 原带是引擎保留区,修复=搬带并永留空。**规则:图形资源"全空区域"一律先做保留区判别再占用;首选离已用区最远的带,并在文档记录保留带坐标**(空轨1st US 图集:y2100–2676 为保留带勿用,本项目改用 y3072 起)。另:图集网格 cell 尺寸必须 ≥ 源字形最大宽高(空轨1st 亚版字形达 51×56,48 网格相邻渗色,用 64);部署脚本幂等判据若只查尺寸/指针不查内容哈希,同尺寸换内容会被跳过——内容级重部署需先卸载再装。
- 通用原则:找到「文本数据表」即接回标准管线;找不到标准载体 → 硬编码/贴图 → 换路线评估。

## 11. 移植到其他游戏的检查清单

- [ ] 引擎与打包形式判定(§3);资源包加密与否?
- [ ] 文本数据载体找到?(否则换路线:数据表编辑或注入,工作量上一档)
- [ ] 两语言导出的列语义确认 + 写回复核
- [ ] **分组顺序:界面文本(菜单/设置/存档)先于剧情对白上线**(§5;玩家最先看到,直观验证双语奏效)
- [ ] **字形覆盖:先查社区"第三语言 mod"的字体管线**(索引表/图集/通道模型,§10 FDK 条目),勿只盯字体包内容;图集先扫空闲带再定可容纳字形数
- [ ] **版式规则套用(§2)**:单行→标题式;含换行→段落式·换行边界;含空行→段落式·空行边界;auto 按组启用
- [ ] 格式/模板键守卫 + 探针法定位手段就位(§4);**printf 占位符守卫:合并结果与原文的 `%` 计数一致,不一致即回滚单语(崩溃级)**
- [ ] 假双语(双无 CJK)自动跳过;占位符/标记结构一致性检查(**校验合并结果,勿只校验单侧**)
- [ ] 部署阶梯:先官方补丁机制 → 重建主资源(先备份!)→ 注入默认排除(§6)
- [ ] 卸载方案 + 平台校验/游戏更新的失效预警;官方哈希基线记录
- [ ] 字体字形覆盖(缺字形 fallback 观感让玩家先确认);固定框溢出由试玩反馈驱动
- [ ] 富文本按 §7、振假名按 §8 判死检查后再决定投入
- [ ] 全程:文本不进上下文、输出过滤、玩家试玩驱动迭代、每步记进度日志
